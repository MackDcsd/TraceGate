# TraceGate V1.0 技术规范白皮书：多维印证协议

本文档定义了 TraceGate 框架在处理复杂工程变更时的核心操作公约。所有接入本门禁的项目必须严格遵守以下两个生命周期。

## 一、 冷启动：苏格拉底式逆向拷问与中央公约

系统拒绝接收一句话的模糊需求。产品经理（人类或 AI）必须通过状态机网络对客户进行穷尽式拷问：
- **无公约，不开发**：项目必须在根目录维护一份静态 `contract.json`（统一数据字典）。
- **示例（以硬件电源变更为例）**：所有团队（前端、后端、中间层、结构）必须强行 `import` 此变量。严禁开发人员在代码或标注里手写字面量（Literal Value）。

## 二、 变更发生：静态图影响分析（Impact Analysis）

当客户提出变更时，系统通过理性的“代码编译器”对源码进行 AST 逆向追踪。

[ 客户变更请求 ] ➔ 触发 TraceGate 编译器
│
┌─────────────┴─────────────┐
▼                           ▼
【静态 AST 语法树分析】      【语义意图知识库比对】
追踪全局变量污染链条           检查业务/设计合同冲突
│                           │
└─────────────┬─────────────┘
▼
【沙箱动态测试桩印证】
│
┌──────────┴──────────┐
[印证失败] ▼             ▼ [印证通过]
Merge 按钮锁死        允许自动代码合并
自动派发联动工单


### 1. 变更分类门禁规则
- **纯粹变更**：经 AST 分析，影响域仅局限在单一小组内（如：纯前端样式修改，测试桩全绿），CI 放行。
- **联动干涉（Critical Impact）**：一旦 AST 发现变更变量跨越了边界（如：中间层驱动参数修改，污染了前端接口），系统必须立刻卡死 Git 合并权限。

### 2. 自动化 Review 工单派发契约
当发生联动干涉时，系统自动反向生成相互锁死的 GitHub Tasks。测试组在测试关联模块时，系统会自动强行注入 Mock 异常数据，直至多维印证数据链完全闭合，门禁方可解除。
